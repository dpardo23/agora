# HU-07.01 · Procesar encargos desde la cola de Supabase

## 1. Descripción

| Parte | Contenido |
|---|---|
| **Plantilla** | Como **dueño del Olimpo**, quiero **que el worker de la VM tome mis encargos de la cola de Supabase y los procese con el pipeline existente**, para **que lo que encargo desde la web se genere sin intervenir en la laptop**. |
| **Contexto** | El paquete `umss` usa hoy una cola en SQLite. Solo cambia el adaptador de cola (arquitectura hexagonal, ADR-002); las verificaciones no se tocan. |
| **Reglas de negocio** | RN-1: el worker llama a `select * from tomar_trabajo('vm-oracle-1')`, que devuelve un trabajo y lo marca `en_proceso` de forma atómica (`FOR UPDATE SKIP LOCKED`). · RN-2: orden FIFO por `creado_en`, respetando `estado_control` (no toma trabajos pausados ni pasos de dioses pausados). · RN-3: lee `agentes.config` al empezar cada paso (HU-05.06). · RN-4: si `aprobar_esquema` está activo, después del paso 3 inserta en `esquemas` (`pendiente`), pone el trabajo en `esperando_aprobacion` y espera; con `cambios_pedidos` regenera el esquema con los comentarios. · RN-5: si el worker se reinicia en mitad de un trabajo, lo retoma desde el último paso `hecho`. · RN-6: un paso que falla 3 veces deja el trabajo en `error` con `detalle`. · RN-7: regla «entrega completa a la primera»: nunca se entrega un PDF con huecos o cajas «Pendiente». |
| **Datos** | `trabajos`, `trabajo_pasos`, `esquemas`, `agentes`. Credenciales por variables de entorno (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `GEMINI_API_KEY`). |
| **Supuestos** | La VM está preparada (T-07). |
| **Fuera de alcance** | Eventos de los dioses (HU-07.02) y entrega (HU-07.03). |

## 2. Criterios de aceptación funcionales (CA-FE)

```gherkin
# language: es
Característica: Procesar encargos desde la cola

  Escenario: CA-FE-01 Tomar un trabajo
    Dado que el #17 está "en_cola"
    Cuando el worker consulta la cola
    Entonces el #17 pasa a "en_proceso" con trabajador "vm-oracle-1"
    Y en la web su estado cambia a "En proceso"

  Escenario: CA-FE-02 Dos workers no toman el mismo trabajo
    Dado dos workers que consultan la cola al mismo tiempo con un solo trabajo
    Entonces solo uno lo obtiene y el otro no recibe filas

  Escenario: CA-FE-03 Esperar la aprobación del esquema
    Dado un trabajo con "aprobar_esquema" activo
    Cuando termina el paso 3
    Entonces el trabajo queda "esperando_aprobacion" y en la web aparece "Revisar esquema"

  Escenario: CA-FE-04 Retomar tras un reinicio
    Dado que el worker se reinicia con el #17 en el paso 5
    Cuando vuelve a arrancar
    Entonces continúa el #17 desde el paso 5 sin repetir los pasos 1 a 4

  Escenario: CA-FE-05 Error tras 3 intentos
    Cuando el paso 7 falla 3 veces
    Entonces el #17 queda en "error" y en la web aparece "Ver error"

  Escenario: CA-FE-06 Trabajo 13 regenerado
    Cuando encargo desde la web el mismo tema del trabajo 13
    Entonces el PDF pasa las mismas verificaciones (citas literales, DOI, barrera de entrega) que en la laptop
```

## 3. Criterios de aceptación no funcionales (CA-NF)

| ID | Atributo | Verificar | Condición | Resultado esperado |
|---|---|---|---|---|
| CA-NF-01 | Fiabilidad | Disponibilidad del worker | systemd con `Restart=always` durante 7 días | Reinicio automático en ≤ 30 s tras una caída |
| CA-NF-02 | Eficiencia | Latencia de toma | Trabajo nuevo con el worker libre | ≤ 10 s (escucha Realtime + sondeo de respaldo cada 30 s) |
| CA-NF-03 | Mantenibilidad | Arquitectura hexagonal | Revisión de código | El dominio no importa `supabase`; solo usa el puerto `Cola` |
| CA-NF-04 | Seguridad | Secretos | Revisión de logs y repositorio | Ningún secreto en logs ni en el código |
