# HU-05.08 · Gestionar los dioses del Olimpo y asignarles roles

## 1. Descripción

| Parte | Contenido |
|---|---|
| **Plantilla** | Como **dueño del Olimpo**, quiero **crear dioses nuevos y asignar o reasignar roles entre ellos**, para **hacer crecer el Olimpo o reciclar a un dios en varias tareas sin tocar el código**. |
| **Contexto** | Pantalla `/olimpo/panteon`. El Olimpo separa dioses y roles (ADR-005): el pipeline apunta a roles y cada rol tiene un dios titular. |
| **Reglas de negocio** | RN-1: la pantalla lista los dioses (retrato, nombre, sala, roles) y los roles (nombre, motor, dios titular, pasos del pipeline que cubre). · RN-2: un rol tiene **un solo** dios titular; un dios puede tener **varios** roles. · RN-3: reasignar un rol con un trabajo en curso se aplica desde el **próximo paso**, nunca en mitad de uno. · RN-4: crear un dios pide nombre (único, de 2 a 30 caracteres), sala, paleta y atributos del sprite desde el catálogo; el escritorio se asigna solo (primer libre de la sala, en módulos de 2). · RN-5: un dios solo se puede retirar si no tiene roles; si los tiene, se pide reasignarlos primero. · RN-6: los cambios se reflejan en la escena en vivo: un dios nuevo entra caminando desde la Recepción. · RN-7: todo cambio queda en `historial_panteon` (quién, qué y cuándo). |
| **Datos** | `dioses(id, nombre, sala_id, escritorio, paleta jsonb, sprite jsonb, activo)`, `roles(id, clave, nombre, motor, config jsonb)`, `asignaciones_rol(rol_id, dios_id, desde)`, `historial_panteon`. |
| **Supuestos** | El catálogo de atributos de sprite (cabeza, túnica, objeto) existe desde el spike T-05. |
| **Fuera de alcance** | Crear roles nuevos: requieren un *handler* en el motor de agentes y se agregan por código con su propio PBI. Configurar un rol (HU-05.06). |

## 2. Criterios de aceptación funcionales (CA-FE)

```gherkin
# language: es
Característica: Gestionar dioses y roles

  Antecedentes:
    Dado que inicié sesión y abrí "/olimpo/panteon"

  Escenario: CA-FE-01 Reciclar un dios con un segundo rol
    Dado que Temis tiene el rol "verificar_citas"
    Cuando asigno el rol "barrera_entrega" a Temis
    Entonces Temis muestra los roles "verificar_citas" y "barrera_entrega"
    Y el paso 8 del pipeline muestra la cara de Temis

  Escenario: CA-FE-02 Reasignar con un trabajo en curso
    Dado que el #17 está ejecutando el paso 4 con Apolo
    Cuando reasigno el rol "redactar" a Calíope
    Entonces veo "Calíope tomará el rol redactar desde el próximo paso"
    Y el paso 4 en curso termina con Apolo

  Escenario: CA-FE-03 Crear un dios nuevo
    Cuando creo el dios "Calíope" en el "Salón de Apolo" con túnica lila y pluma
    Entonces Calíope entra caminando desde la Recepción hasta el primer escritorio libre del Salón de Apolo

  Esquema del escenario: CA-FE-04 Validación del nombre
    Cuando escribo <nombre> como nombre del dios
    Entonces veo <mensaje>

    Ejemplos:
      | nombre | mensaje                                   |
      | Z      | El nombre debe tener entre 2 y 30 caracteres. |
      | Apolo  | Ya existe un dios llamado Apolo.          |

  Escenario: CA-FE-05 Retirar un dios con roles
    Dado que Hermes tiene el rol "recibir_avisos"
    Cuando intento retirar a Hermes
    Entonces veo "Reasigna sus roles antes de retirarlo: recibir_avisos."
```

## 3. Criterios de aceptación no funcionales (CA-NF)

| ID | Atributo (ISO/IEC 25010) | Verificar | Condición | Resultado esperado |

| CA-NF-01 | Mantenibilidad · modificabilidad | Agregar un dios | Revisión del diff | 0 líneas de código cambiadas: solo datos |

| CA-NF-03 | Eficiencia | fps con 20 dioses | Escritorio de gama media | ≥ 60 fps p95 en la planta visible |

## 5. Notas técnicas

`PUT /api/v1/roles/{id}/asignacion`, `POST /api/v1/dioses`, `DELETE /api/v1/dioses/{id}` (`docs/api.md`). Feature `src/features/olimpo/panteon`. El render lee el catálogo de dioses al vuelo; la hoja de sprites se regenera solo para el dios nuevo.
